## 1. 파이프라인 개요

```
[CCTV] → [프레임분할] → [객체디텍팅] → [오분류 판정]
  ├─ 탐지 시 → [현장알림: 전구+경고음]
  └─ 결과전송 → [백엔드: 수신API → 기록/통계]
→ [관리자웹: 스트리밍·기록·통계, 오분류 시 테두리 빨간색]
```

- 목적: 행정직원 분리수거 감독 부담 경감
- 알림 수단: 전구 + 스피커 (항상 둘 다 트리거)
- 안면 인식(투기자 식별)은 본 파이프라인 미포함, CTO 공통과제는 3팀 소관

## 2. 설치 환경

| 항목 | 내용 |
|---|---|
| 설치 위치 | 엘리베이터 앞 2대(`ELEV-01`,`ELEV-02`), 4층 휴게실 1대(`REST-4F-01`) |
| 메인보드 | NVIDIA 젯슨 나노(Jetson Nano) — 입고까지 약 2주 소요 |
| 배포 구조 | 설치 위치 3곳에 각각 메인보드+웹캠 독립 제공 (각 위치가 독립된 물리 캡처 소스) |
| 클래스(1차) | general, paper, plastic(coffeeCup 별도), mixed, uncertain |

## 3. 추론 인프라 (L40S x4, 1장만 할당)

- 학원 보유 **NVIDIA L40S 4장(GPU 서버)**를 객체 탐지 모델 추론용으로 사용, Docker로 운영
- **다른 팀들과 서버를 공유**하기 때문에 4장 중 **1장만 할당받아 사용** — 모델
  학습, DB 저장, 백엔드 배포를 전부 이 1장(할당된 리소스) 안에서 처리
- 메인보드 3대는 각각 RTSP로 영상을 중앙 백엔드에 전송 → **중앙(GPU 서버)에서 탐지 수행**
  (엣지 추론 아님)
- 객체 탐지 모델/프레임워크 자체는 아직 보류 (YOLO 계열 후보뿐, 미확정) — 확정 전
  임의 구현 금지

## 4. 배포 전략

- 개발: Windows 노트북에서 Docker로 진행 (로컬 웹캠으로 우선 테스트)
- 배포: 동일 Docker 이미지를 그대로 GPU 서버(Linux, L40S x4 중 할당받은 1장)로 이전
- MVP 단계: **백엔드(FastAPI) + 모델 학습 + DB 저장 + 탐지 추론을 할당받은
  GPU 1장 안에 전부 통합 배포** (다른 팀과 공유하는 서버라 4장 중 1장만
  사용, 별도 상시 서버 불필요)
- GPU 패스스루: `nvidia-docker`(NVIDIA Container Toolkit) 필요
- 영상 소스는 `.env`의 `CAMERA_SOURCE` 값만 환경별로 다르게 관리 (로컬 웹캠 vs
  RTSP 수신/샘플 영상), 코드 변경 없음

## 5. 개발 단계 웹캠 시뮬레이션

메인보드 입고 전까지 보유 중인 외장 웹캠 1개를 노트북에 연결해 파이프라인을
먼저 개발/검증한다.

- 동일 웹캠을 동시에 여러 번 열 수 없는 OS 제약 때문에, 캡처는 한 번만 열고
  얻은 프레임을 3개 카메라ID(`ELEV-01`/`ELEV-02`/`REST-4F-01`)에 복제해서 제공
- 메인보드 입고 후엔 이 부분만 CameraId별 독립 RTSP 소스로 교체 (다른 계층은
  변경 불필요)
- `cv2.VideoCapture().read()`는 동기 블로킹 — `async def` 안 직접 호출 금지,
  `asyncio.to_thread()`/스레드 분리 필수

## 6. 젯슨 나노 엣지 코드 (별도 개발 필요)

입고 전이라 아직 실행 불가하지만, 입고 후 아래 2가지를 직접 개발해야 함:

1. **웹캠 캡처 → RTSP 송신**: JetPack 기본 포함된 GStreamer 기반으로 구현 예정.
   1단계(웹캠 뷰어, Python 3.11)는 노트북에서 테스트 완료.
2. **중앙 서버의 알림 신호 수신 → GPIO로 전구/경고음 실제 트리거**: 아직 설계
   전. `RPAs/alertController.py`는 중앙 백엔드 안에서 Mock 처리하는 자리만
   잡아둔 상태 — 실제로는 젯슨 나노 쪽 리스너로 옮겨야 할 가능성 높음.
   신호 전달 방식(MQTT/HTTP/WebSocket)은 TBD.

## 7. 현장 알림(RPA) 정책

- 오분류 탐지 시 즉시 전구점등+경고음 둘 다 자동 트리거 (관리자 재전파 없음)
- 수거 모드(`COLLECT`) 활성화 시: 전구/스피커/화면 테두리 알림 전부 Mute,
  단 오분류 탐지 로직 자체는 계속 동작 (통계만 갱신, 알림/UI 트리거 단계에서만
  모드 확인 후 스킵)

## 8. 이벤트 적재 정책

- 매 프레임 Insert 금지 — 이벤트 발생 시점만 저장
- 동일 카메라+클래스 **5초 Cooldown** (조정 여부 TBD)
- 이미지 저장은 MongoDB GridFS 확정
- 학습용 원본 이미지 저장 방식은 별도 TBD (MongoDB GridFS 재사용 vs GPU 서버
  로컬 디스크에 파일로 축적 — 논의 중)

## 9. Event Flow (고정)

```
Detect → Create Event → Save Event
→ Check SystemState.mode
    ├─ COLLECT(수거모드): 통계만 갱신 (Broadcast/RPA 스킵)
    └─ MANAGE(관리모드): WebSocket Broadcast + RPA 트리거 → 통계 갱신
```

| MongoDB 호스트 포트 | **27020** | 컨테이너 내부는 27017 유지, 팀 간 충돌 방지 |

## 11. DB 접속 방식 (팀 공유 vs 로컬)

- `.env`의 `MONGO_HOST`/`MONGO_PORT`/`MONGO_USER`/`MONGO_PASSWORD`를
  팀원마다 각자 환경에 맞게 설정
  - 팀 공유 서버로 테스트: `MONGO_HOST=192.168.0.30`
  - 본인 로컬 Docker(`my-mongo`)로 테스트: `MONGO_HOST=localhost`
- `infra/checkEnv.py`, `debug/testDbConnection.py`, `debug/testCrud.py`
  세 스크립트가 모두 같은 `.env` 키를 공유 (서로 다른 대상을 보면 결과가
  엇갈릴 수 있으니 주의)
- 원래 Atlas로 테스트하던 디버그 스크립트는 로컬/자체 Docker MongoDB로
  전환됨 (`mongodb+srv://` → `mongodb://` + 명시적 포트)
