# 프로젝트 컨텍스트 문서 (AI 개발 참고용)
> 이 문서는 바이브 코딩(AI 코딩 어시스턴트) 세션 시작 시 프로젝트 메모리로 사용합니다.
> Claude Code / Cursor 등에서 `CLAUDE.md` 또는 `.cursorrules` 등으로 저장해서 사용하세요.

## 0. 이 문서의 목적
AI가 매 세션마다 프로젝트 배경을 새로 추측하지 않도록, 다음을 고정 컨텍스트로 제공합니다:
- 프로젝트 목적과 범위
- 데이터 파이프라인 구조
- DB 스키마 및 기술 스택 결정 사항
- 아직 결정되지 않은 것(TBD) — AI가 임의로 결정하지 않고 반드시 질문하도록 유도

## 1. 프로젝트 개요

- **팀**: 1팀
- **프로젝트명**: CCTV 기반 올바른 쓰레기 분리수거 탐지 및 자동 경고 시스템
- **목적**: 행정직원의 분리수거 감독/재전파 업무 부담 경감, 분리수거 효율화
- **핵심 흐름**: CCTV 실시간 영상 → 객체 탐지(쓰레기 분류) → 오분류 판단 → **전구 점등 + 경고음 출력(현장 알림)** + 관리자 페이지 실시간 알림 → DB 통계 적재 → 대시보드 시각화
- **알림 수단**: 스피커(경고음)뿐 아니라 **경고 전구(점등)** 도 함께 사용 (팀에서 전달받은 아키텍처 다이어그램 기준)
- **관리자 페이지 UI 요구사항**: 오분류 탐지 시 관리자 페이지의 **실시간 스트리밍 화면 테두리를 빨간색으로 표시**
- **안면 인식 범위**: 본 프로젝트(분리수거 탐지)의 메인 파이프라인에는 안면 인식이 포함되지 않음. CTO 공통 과제로 안면 인식 모델(ArcFace 등) 성능 비교가 별도로 있으나, 이는 3팀(출결 관리) 과제이며 **1팀 레포에는 포함하지 않는 것을 기본값**으로 함. '투기자 식별/추적' 기능으로 추후 확장할지는 TBD (팀 논의 필요)

## 3. 시스템 아키텍처

> 아래는 팀이 전달한 아키텍처 다이어그램(간이 흐름도 + 상세 컴포넌트도)을 기준으로 재정리한 구조입니다.

### 3-1. 컴포넌트 구성
전체 시스템은 5개 컴포넌트로 구성됩니다.

1. **실시간 객체 디텍팅 시스템**: 실시간 영상 수신 → 프레임 분할 → 객체 디텍팅 모델 → 디텍팅 결과 생성 → 오분류 탐지 여부 판정
2. **데이터 저장소**: 이미지 저장소(오분류 시점 이미지) + 기록 데이터베이스(MongoDB, 이벤트/통계)
3. **현장 물리 알림 시스템**: 알림 제어 모듈 → **전구 점등** + **경고음 출력** → 쓰레기통 현장의 경고 전구·경고 스피커 구동
4. **백엔드 서버**: 실시간 영상 전송, 결과 수신 API, 기록 관리, 통계 처리
5. **관리자 웹 시스템**: 메인 관리자 페이지 → 좌측 사이드바(이전 기록→기록 상세, 수거 모드/관리 모드) / 실시간 스트리밍 / 통계 대시보드. 오분류 탐지 시 스트리밍 화면 테두리 빨간색 표시

### 3-2. 흐름도 (개요)
```
[CCTV 실시간 촬영]
    → [영상 프레임 분할] → [객체 디텍팅]
    → [오분류(위험 객체) 탐지 여부 판정]
        ├─ 탐지 시 → [현장 물리 알림: 전구 점등 + 경고음 출력]
        └─ 결과 전송 → [백엔드 서버: 결과 수신 API → 기록 관리 / 통계 처리]
    → [관리자 웹 시스템: 실시간 스트리밍·기록·통계 표시, 오분류 시 영상 테두리 빨간색]
```

### 3-3. 상세 데이터 흐름 (컴포넌트 간 연동)
```
실시간 객체 디텍팅 시스템
    ├─ 실시간 영상            → 백엔드(실시간 영상 전송) → 관리자 웹(실시간 스트리밍)
    ├─ 결과 전송(오분류 상태)   → 백엔드(결과 수신 API) → 관리자 웹(오분류 시 테두리 빨간색 표시)
    ├─ 오분류 객체 탐지         → 현장 물리 알림 시스템(알림 제어 모듈)
    │                              ├─ 전구 점등 → 경고 전구 (쓰레기통 현장)
    │                              └─ 경고음 출력 → 경고 스피커 (쓰레기통 현장)
    └─ 이미지 저장             → 데이터 저장소(이미지 저장소)

백엔드 서버
    ├─ 결과 수신 API 수신 데이터 → 데이터 저장소(기록 데이터베이스) + 통계 처리
    └─ 기록 관리 → 관리자 웹(이전 기록 → 기록 상세)
```

### 3-4. 물리 파이프라인 (RTSP 수신 레이어, 하드웨어 관점 보충)
```
CCTV (RTSP)
    → OpenCV로 영상 수신 (실시간 객체 디텍팅 시스템 내부)
    → 프레임 단위 AI 모델 추론 (Inference)   ⚠️ 모델 자체는 아래 참고 — 보류 상태
```
> ⚠️ **객체 탐지 모델은 아직 팀 내 논의가 더 필요해 보류 상태입니다.** YOLO 버전, 커스텀 학습 여부, 클래스 매핑 등 모델 관련 결정은 확정 전까지 AI가 임의로 구현하지 말 것 (4-1, 9번 참고).
- **MVP 단계(8/7~8/10)**: 실제 CCTV 대신 노트북 웹캠 또는 `/videos/sample.mp4` 테스트 동영상 파일을 읽어 스트림을 흉내 내는 **Mock Streaming**으로 개발. 이때 FPS를 제한(예: 초당 5~10프레임)해서 추론 부하를 줄일 것
- **모델 미확정 상태에서의 개발 진행 방식**: 프론트/백엔드/DB/알림 파이프라인은 모델과 무관하게 먼저 개발 가능 — 탐지 결과 자리에 **랜덤/더미 분류 결과**(예: 클래스 중 무작위 선택 + 임의 confidence)를 반환하는 Mock 추론 함수로 대체해서 나머지 파이프라인을 먼저 완성할 것. 실제 모델은 확정되는 대로 이 Mock 함수만 교체
- **탐지 시스템 ↔ 백엔드 서버 분리 여부**: 다이어그램상 별도 컴포넌트로 분리되어 있으나(결과를 API로 전송), 실제 구현 시 하나의 FastAPI 프로세스 내 모듈로 둘지 별도 프로세스/서비스로 둘지는 **TBD** (9번 참고). MVP 단계에서는 한 프로세스 내 모듈 분리로 우선 구현 권장
- **⚠️ OpenCV 블로킹 방지**: `cv2.VideoCapture().read()`는 동기 블로킹 함수라 FastAPI `async def` 안에서 직접 호출하면 서버 전체(WebSocket 포함)가 멈출 수 있음 — 반드시 `asyncio.to_thread()` 또는 별도 스레드로 프레임 획득 로직을 분리할 것 (8번 규칙 18 참고)

### 3-5. 현장 알림(RPA) 구현 방식
- **RPA 트리거 조건**: 오분류(위험 객체) 탐지 시 즉시 현장 알림 — **전구 점등 + 경고음 출력 둘 다** 수행 (관리자 재전파 없이 자동 대응이 핵심 목적)
- **RPA 구현 방식 (MVP 기준)**: 별도 HW/Webhook 없이, 백엔드/디텍팅 로직에서 `RPAs/alertController.py`를 비동기(async)로 직접 호출. 내부적으로 `soundPlayer`(로컬 오디오 파일 재생)와 `lightController`(경고등 제어, MVP 단계에서는 콘솔 로그/모의 신호로 대체 가능 — 실제 GPIO/HW 제어는 TBD) 두 기능을 모두 트리거

### 3-6. 이벤트 적재 정책 (DB 과부하 방지)
- 매 프레임(초당 다수 회)마다 DB에 Insert하지 않음 — **오분류/이벤트 발생 시점에만** 기록 데이터베이스(MongoDB)에 저장
- **Cooldown(중복 방지)**: 동일 카메라·동일 클래스에서 오분류가 연속 발생해도 **5초간은 재알림/재적재하지 않음** (기본값 5초, 필요 시 조정)
- **이미지 저장소**: 오분류 탐지 시점의 이미지를 기록 데이터베이스와 별도로 저장. **MongoDB GridFS 사용 확정** — 별도 스토리지 인프라 없이 기존 MongoDB Docker 컨테이너를 그대로 재사용. 이벤트 발생 시점에만(초당 프레임 아님) + 5초 Cooldown 적용되어 저장 이미지 수가 많지 않으므로 이 규모에 적합
- **⚠️ Mock 단계에서의 이미지 처리**: DB(GridFS) 연동 전까지는 `imageFileId` 대신 **더미 이미지 경로**(예: `/debug/assets/sample_misclassified.jpg`)를 Mock API가 반환하도록 구성할 것. GridFS 실제 연동은 DB 연동 확정 시점에 이 더미 경로만 교체

- **오탐/복합 쓰레기 전용 DB**를 별도로 구축해 통계 대시보드에서 시각화 (회의 피드백 반영)

### 3-7. WebSocket 이벤트 메시지 규격 (백엔드 → 프론트엔드, 초안)
> 프론트/백엔드 간 이벤트 키값이 어긋나지 않도록 아래 포맷을 고정 적용

```json
{
  "eventType": "MISCLASSIFICATION_DETECTED",
  "cameraId": "ELEV-01",
  "timestamp": "ISO8601",
  "isMisclassified": true
}
```
- `eventType`은 대문자 스네이크케이스(예: `MISCLASSIFICATION_DETECTED`)로 통일 — 이벤트 종류 구분용 상수이므로 7번 camelCase 규칙의 예외로 허용
- 필드값(`cameraId` 등)은 기존 camelCase 규칙 유지
- 새로운 이벤트 타입 추가 시 이 표에 먼저 추가 후 구현할 것 (AI가 임의로 새 `eventType` 문자열을 만들지 말 것)

### 3-8. 수거 모드 동작 정의
- **수거 모드 활성화 시**: 작업자가 쓰레기통을 비우는 중이므로, 현장 알림(전구 점등·경고 스피커)과 관리자 페이지 화면 테두리 빨간색 표시를 **일시 정지(Mute)** 처리한다
- 즉, 오분류 탐지 로직 자체는 계속 동작해도 되지만, **알림/UI 경고 트리거 단계에서 수거 모드 여부를 먼저 확인**하고 수거 모드면 알림을 스킵할 것
- 관리 모드로 복귀 시 알림 정상 재개

### 4-1. 언어/런타임 버전 (팀 확정 필요 — 착수 전 반드시 명시할 것)

## 5. DB 스키마 (⚠️ 보류 — 실제 연동은 나중에, 우선 Mock 데이터로 개발)

> **DB(MongoDB) 실제 연동은 보류 상태입니다.** 아래 스키마는 참고용 초안이며, 최종 확정 전까지 AI는 실제 MongoDB 연결 코드를 작성하지 말고 **인메모리(In-memory) 리스트나 Mock 함수로 데이터 계층을 대체**해서 나머지 파이프라인(프론트/백엔드 API/알림)을 먼저 완성할 것. 실제 DB 연동은 스키마 확정 후 이 Mock 계층만 교체.
> 필드명은 네이밍 컨벤션(8번 규칙)에 따라 camelCase로 통일

{
  "eventId": "string (uuid)",

  "cameraId": "string (예: ELEV-01, ELEV-02, REST-4F-01)",
  "detectedClass": "general | paper | plastic | coffeeCup | mixed | uncertain",
  "isMisclassified": "boolean",
  "confidenceScore": "float",
  "actionTaken": "lightAndSound | soundOnly | lightOnly | notificationOnly | none",

## 8. AI에게 요청할 때 지켜야 할 규칙 (가이드라인)

1. **클래스 정의가 최종 확정되기 전까지** 임의로 클래스를 추가/변경하지 말 것 — 반드시 질문할 것
2. **DB 스키마 변경 시** 위 초안을 기준으로 하되, 임의 필드 추가는 사용자 확인 후 진행. **단, DB 실제 연동 자체가 보류 상태이므로 확정 전까지는 실제 MongoDB 연결 코드를 작성하지 말고 인메모리/Mock 데이터 계층으로 대체할 것** (5번 참고)
3. 개발 환경은 Windows 로컬 + Docker(DB 전용)를 벗어나지 않을 것 (전체 컨테이너화 등 제안 시 먼저 확인)
4. RPA/알림 로직은 "오분류 즉시 현장 경고"가 핵심 요구사항임을 항상 고려할 것. **단, 수거 모드 활성화 중에는 전구·스피커 알림과 화면 테두리 경고를 Mute 처리할 것** (3-8 참고)
5. **`.env`와 CCTV 영상 파일은 절대 Git에 커밋하는 코드/명령을 생성하지 말 것** — `.gitignore`에 반드시 포함된 상태를 유지
6. 위 폴더 구조(`WebApps/`, `Docs/`, `RPAs/`, `debug/`, `videos/`, `.agentfiles/`)를 벗어난 임의 폴더 생성 전 사용자 확인
7. **네이밍 컨벤션: 변수/함수는 `camelCase`, 클래스명은 `PascalCase`(대문자로 시작하는 카멜케이스) 사용** — Python 기본 관례(PEP8 snake_case)와 다르므로, Python 코드 작성 시에도 AI가 임의로 `snake_case`로 바꾸지 않도록 항상 이 규칙을 적용할 것. DB/JSON 필드명도 프론트-백엔드 일관성을 위해 camelCase로 통일
   - **예외**: FastAPI/Pydantic 등 프레임워크가 강제하는 이름(예: `__init__`, `lifespan`, dunder 메서드)이나, Pydantic `BaseModel`의 내부 snake_case 필드를 camelCase로 노출해야 할 때는 `Field(alias=...)`를 사용할 것 — 프레임워크 자체 관례를 깨지 말 것
8. 아래 TBD 항목은 코드에 하드코딩하지 말고 설정값(config)으로 분리할 것
9. **RPA(현장 알림)는 별도 HW/Webhook 없이 `RPAs/alertController.py`를 비동기 호출하는 방식으로 우선 구현하며, 전구 점등과 경고음 출력을 모두 트리거할 것** — 스피커만 구현하고 전구를 누락하지 말 것. HW/Webhook 방식으로 임의 변경 금지 (변경 시 사용자 확인)
10. **DB 적재는 매 프레임이 아닌 이벤트 발생 시점에만, 동일 카메라·클래스 5초 Cooldown 적용** — 이 로직 없이 프레임마다 Insert하는 코드 생성 금지
11. **MVP 단계 영상 처리는 Mock Streaming(웹캠 또는 `/videos/sample.mp4`) 기준, FPS 제한(초당 5~10프레임) 적용** — 실제 CCTV/RTSP 연동 코드는 CCTV 입고 전까지 생성하지 말 것
12. 4-3에서 연결 여부가 확정되지 않은 MCP(MongoDB MCP 등)를 이미 연결된 것처럼 가정하고 코드/설명을 생성하지 말 것
13. **관리자 웹 프론트엔드에서 오분류 탐지 시 실시간 스트리밍 화면 테두리를 빨간색으로 표시**하는 요구사항을 항상 반영할 것 (다이어그램 기준 확정 요구사항)
14. **객체 탐지 모델은 보류 상태 — 팀 내 추가 논의 후 확정 예정.** 모델 학습, 특정 프레임워크(YOLO 등) 설치/코드 작성, 클래스 매핑 로직을 AI가 임의로 진행하지 말 것. 나머지 파이프라인(프론트/백엔드/DB/알림) 개발 시에는 3-4에 명시된 **Mock 추론 함수(랜덤/더미 분류 결과)** 로 대체해서 진행할 것
15. **백엔드→프론트 WebSocket 메시지는 3-7의 고정 포맷(`eventType`, `cameraId`, `timestamp`, `isMisclassified`)을 따를 것** — 새 이벤트 타입이 필요하면 임의로 만들지 말고 먼저 문서(3-7)에 추가 후 구현
16. **Mock 단계에서 이미지가 필요한 응답은 GridFS `imageFileId` 대신 더미 이미지 경로를 반환할 것** (3-6 참고) — GridFS 실제 코드는 DB 연동 확정 전까지 작성 금지
17. **CORS**: 백엔드(FastAPI) 작성 시 로컬 개발 편의를 위해 `CORSMiddleware`를 초기 세팅에 포함할 것 (프론트 Vite 개발 서버 `http://localhost:5173` ↔ 백엔드 `http://localhost:8000` 간 포트가 다름). 개발 단계에서는 `http://localhost:5173` 허용(또는 `*`)으로 시작하고, 배포 시 Origin을 좁힐 것
18. **OpenCV 블로킹 방지**: `cv2.VideoCapture().read()`는 동기 블로킹 함수이므로, FastAPI의 `async def` 핸들러/WebSocket 루프 안에서 직접 호출하지 말 것. 프레임 획득은 `asyncio.to_thread()` 또는 별도 `threading.Thread`로 분리해서, 메인 이벤트 루프가 멈추지 않도록 구현할 것
19. **환경변수**: 프로젝트 루트에 `.env.example`을 유지하고, 새 환경변수가 추가될 때마다 `.env.example`도 함께 갱신할 것 (실제 값은 절대 포함하지 말 것, `.env`는 Git 제외)
20. **API는 11번 명세에 고정된 엔드포인트만 사용할 것** — 유사한 이름(`/detect`, `/misclassification` 등)을 임의로 만들지 말고, 새 엔드포인트가 필요하면 먼저 11번 표에 추가 후 구현
21. **비즈니스 로직은 반드시 Controller → Service → Repository 순서를 따를 것** — Controller(API 라우터)에서 DB/Repository에 직접 접근하는 코드 작성 금지 (14번 참고)
22. **22번(금지사항) 목록을 항상 우선 확인할 것** — 특히 라이브러리 임의 추가, 폴더/API/Event Flow/DB Schema/네이밍/Camera ID 변경은 사용자 확인 없이 진행 금지

## 11. API 명세 (고정 — AI가 임의로 새 엔드포인트를 만들지 말 것)

> 아래 목록이 확정된 API 전체입니다. `POST /detect`, `POST /event` 같은 유사 이름을 임의로 만들지 말고, 새 API가 필요하면 먼저 이 표에 추가한 뒤 구현할 것.

| Method | Path | 설명 |
|---|---|---|
| GET | `/api/stream` | CCTV 영상 스트림 (MJPEG) |
| POST | `/api/events` | 오분류 이벤트 생성 (디텍션 시스템 → 백엔드) |
| GET | `/api/events` | 이벤트 목록 조회 (이전 기록) |
| GET | `/api/events/{id}` | 이벤트 상세 조회 (기록 상세) |
| GET | `/api/statistics` | 통계 데이터 조회 (통계 대시보드) |
| POST | `/api/mode` | 관리모드/수거모드 전환 |
| WS | `/ws/events` | 실시간 이벤트 브로드캐스트 (3-7 메시지 규격 사용) |

## 12. Event Flow (이벤트 기준 처리 순서 — 고정)

> AI는 아래 순서를 임의로 재배치하거나 단계를 생략하지 말 것

```
Detect (객체 디텍팅 모델 추론)
    ↓
Create Event (오분류 판정 시 이벤트 객체 생성)
    ↓
Save Event (기록 데이터베이스 저장 — 현재는 Mock/인메모리, 5번·9번 참고)
    ↓
Broadcast WebSocket (관리자 웹으로 실시간 전송, 3-7 규격)
    ↓
Trigger RPA (전구 점등 + 경고 스피커, 단 수거모드 중엔 Mute — 3-8 참고)
    ↓
Update Statistics (통계 집계 갱신)
```
- 각 단계는 독립 함수/서비스로 분리해서 구현할 것 (14번 아키텍처 원칙 참고)

## 13. Camera ID 규칙 (고정 — 절대 변경 금지)

## 14. 아키텍처 원칙 (레이어 규칙 — 고정)

```
AI Model (Mock 또는 실제 탐지 모델)
    ↓
Detection Service
    ↓
Event Service
    ↓
RPA Service
    ↓
Repository (현재는 인메모리/Mock, DB 확정 시 MongoDB로 교체)
    ↓
MongoDB (보류 상태 — 5번, 9번 참고)
    ↓
WebSocket
    ↓
Frontend
```

- **Controller → Service → Repository** 흐름을 강제한다. **Controller(API 라우터)에서 DB/Repository에 직접 접근하는 코드 금지** — 반드시 Service를 거칠 것
- `backend/` 디렉터리 역할 세분화:
```
backend/
├── controllers/    # API 라우터 (요청/응답 처리만, 비즈니스 로직 금지)
├── services/       # 비즈니스 로직 (Detection/Event/RPA Service 등)
├── repositories/   # 데이터 접근 계층 (현재 Mock/인메모리 구현)
├── models/         # Pydantic 모델/스키마
├── websocket/      # WebSocket 연결 및 브로드캐스트 관리
├── streaming/       # MJPEG 스트리밍 관련 로직
└── utils/          # 공통 유틸리티
```

## 15. 상태(State) 정의 (고정)

**SystemState** (카메라/시스템 상태)
- `MONITORING` — 평상시 모니터링 중
- `ALERTING` — 오분류 탐지되어 알림 발생 중
- `COLLECTING` — 수거 모드로 알림 Mute 중 (3-8 참고)
- `OFFLINE` — 카메라 연결 끊김

**Mode** (관리자 페이지 모드, `POST /api/mode`로 전환)
- `MANAGE` — 관리 모드 (기본값)
- `COLLECT` — 수거 모드

## 16. Enum 정의 — `eventType` (고정, 3-7 확장)

- `MISCLASSIFICATION_DETECTED` — 오분류 탐지

## 17. 에러 처리 정책

- **카메라 연결 실패**: 재시도 → 30초간 재시도 실패 시 `CAMERA_DISCONNECTED` 이벤트 발생 + 관리자 알림 (WebSocket 브로드캐스트)
- **DB(Repository) 저장 실패**: 우선 메모리 캐시에 임시 저장 → 재시도. (현재 DB 자체가 Mock/보류 상태이므로, 이 정책은 실제 MongoDB 연동 확정 후 적용)

## 23. 용어집 (Definition)

| 용어 | 정의 |
|---|---|
| Object Detection | 객체 탐지 |
| Misclassification | 잘못 버려진 쓰레기(오분류) |
| Event | 오분류 발생 기록 |
| Alert | 현장 알림 (전구 점등 + 스피커) |
| Record | DB(기록 데이터베이스)에 저장된 데이터 |
| Statistics | 집계 데이터 (통계 대시보드용) |
| Stream | 실시간 영상 (MJPEG) |
| RPA | 현장 물리 알림 시스템 (전구·스피커) |

> AI가 `Detection`/`Alarm`/`Warning`/`Notice`/`Notification` 등을 혼용하지 않도록, 위 용어 외의 유사어는 사용하지 말 것
